# The shared workspace

Every client of a profile (desktop, phone) sees one workspace: the same open and
pinned tabs, the same tool settings and prompts, the same recents. A change on one
client appears on the others within about a second. Each client still decides what
it's looking at.

## What's shared and what isn't

**Shared, on the server:** what you're working on, and how you like your tools to
behave. Tabs, tool working state, LoRA pools, recents, tool preferences, drafts,
"already seen" hints.

**Per client, in local storage:** what this screen and hardware are like, and where
this client is looking right now. Panel widths, volume, current route, active project,
filters, theme, PINs, credentials, paths on this machine.

`frontend/src/utils/stateRegistry.ts` declares which side every key is on, and a test
fails on a key it doesn't list. Adding persisted state means choosing a side.

## How it works

The server keeps `workspace_docs`, one row per `(namespace, key)` holding JSON, in the
profile's database:

| Namespace | Holds |
|---|---|
| `tab` | One sidebar tab, keyed by tab id |
| `kv` | Anything else shared, named by its storage key without the server and profile scope |
| `blob` | A reference (`hash`, `size`) to a file in `<profile>/workspace_blobs/`, for masks and paint layers |

`frontend/src/utils/workspaceStore.ts` holds these in memory so reads stay synchronous.
`syncedStorage` has the same interface as `localStorage` and takes the same keys.

**Writes** send only the top-level keys that changed, in batches. Writing what's already
there sends nothing. **Conflicts** are per top-level key, and the last write to reach the
server wins. There's no CRDT, because one person moves between clients. A key changed
here and not yet acknowledged is kept over anything arriving. The prompt also waits for
the cursor to leave the field.

**Events:** `workspace_docs_changed` carries each change and the writer's client id, so a
client ignores its own. A client that reconnects re-reads everything, and the server
keeps no replay log.

**Loops:** applying another client's change can rewrite values (constraints,
normalization). Those rewrites aren't sent, and a write that changes nothing is dropped by
the server without a broadcast. Two clients can't correct each other indefinitely.

**Closing a tab** soft-deletes its row. It can be reopened, with its state, from any
client for 30 days, after which the server purges it, the tool state only it used, and any
stored files nothing else references.

**Tool tab ids** are generated by clients and unique without coordination. Older tabs keep
the integers they had.

**Job feeds** span clients. A generator instance id is `tool-<scope>@@<client>`, and a tool
tab follows `<scope>`, so a job started on the phone shows live in the desktop's tab.
Generate forever stays with the client that armed it.

## Migration

The first time a client opens a profile on a server with a workspace, it may upload what
it kept locally (`frontend/src/utils/workspaceBoot.ts`, `backend/workspace_service.py`):

- **One claim per profile,** decided in one transaction. A partial import can't happen.
- **Only a desktop with tabs can claim.** Phones never do, so launch order doesn't matter.
- **Additive.** An import doesn't overwrite what's on the server, so tabs made on a phone
  first are kept.
- **Allow-listed.** Only keys `stateRegistry` marks as migrated leave the client, and only
  for this server and profile. A closed tab's data stays behind.
- **Checked.** Tabs for deleted chats, collections, flows, projects and assets are dropped.
- **Archived, not merged.** A later desktop's upload is kept in `workspace_migrations`, and
  it takes on the shared workspace.
- **Reversible.** Local copies aren't touched, so downgrading still has its workspace.
  Changes made after migrating don't travel back.

`pinned_tools` rows become pinned tabs on the first read of a profile. Tabs are then the
authority, and the old pin endpoints exist for older desktops.

`stimma doctor workspace [--from DIR]` reports what a store would carry over, read-only,
with names and sizes only.

## Versions

A server advertises `workspace_sync` in its settings. A client talking to a server without
it stays on local storage, under the same keys as always. An older desktop on a newer
server keeps working on its own local storage and `pinned_tools`, without syncing.

- `backend/tests/test_workspace.py`: the API, merges, the claim, purge.
